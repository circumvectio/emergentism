Evidence tier [B] — file-path evidence

The Pipeline

The public surface is a bounded set of static files. Small Python builders maintain its route index and offline cache; a copy-only builder assembles the allow-listed release; the release gate then checks the declared contract. No database, CMS, or network call is required to build or verify the local candidate.

Step 1 build_pwa.py

Maintains the web manifest and offline cache; --check detects drift without rewriting them.

→
Step 2 build_atlas_index.py

Maintains the route atlas; --check verifies it against the public route contract.

→
Step 3 build_release.py

Copies only the allow-listed release files into a deterministic candidate bundle.

→
Step 4 predeploy_check.py

Checks the exact tree and hash, purity rules, links, metadata, route reachability, and archive boundary.

→
Step 5 audit_live_domain_against_manifest.py

Optionally compares a named live URL byte-for-byte with the already-built candidate. Deployment remains separate.

[S] These scripts are committed to the repository at the root of 12_PUBLIC_SITE/ (build_pwa.py, build_atlas_index.py, build_release.py, predeploy_check.py, and the live-domain auditor). No claim about the pipeline requires trust — only source inspection and a reproduced build.

Evidence tier [A] — enforced by code

The Gate

predeploy_check.py is the last local check before a deploy command. It exits nonzero when any implemented condition below is violated. A pass does not authorize or prove deployment.

⊘

No external runtime resources

Stylesheets, scripts, fonts, images, modules, and fetched code must resolve inside the bundle. Ordinary external hyperlinks remain allowed. [A]

✓

Tier-marker presence

Each claim-bearing route covered by the gate must contain at least one visible evidence-tier marker. The gate does not validate every sentence or infer its correct tier. [A]

▣

Manifest boundary

The output must equal the route, root-file, and asset allowlist exactly. Archive roots and undeclared files fail the gate; authorization remains a separate human act. [A]

⌘

Link integrity

Internal file targets and fragments are checked, as are referenced CSS and JavaScript dependencies. The gate does not certify the content or availability of ordinary external links. [A]

◈

Purity negatives

Named external-system leakage and a bounded list of retired claim patterns fail the build. This is a source-negative check, not a complete semantic or historical audit. [A]

⚡

Deterministic tree hash

The builder writes RELEASE_SHA256; the gate recomputes the digest over every other released path and byte. It is an integrity check, not a signature or publication receipt. [A]

build and gate — output shape (your digest differs) 
$ python3 -B build_release.py
release files=<count> sha256=<digest>
$ python3 -B predeploy_check.py --release .release
PASS: pure release routes=<count> files=<count> sha256=<digest>
# The gate reports only implemented checks; run it for current values.

Evidence tier [S] — functional role map

The Seven-Role Dispatch

The Rosetta is not an authorization system. It is a functional role map — seven jobs that can be filled before any document ships: Firewall, Truth-Cut, Audit, Executor, Architect, Compressor, Witness. On this project, the roles may be performed by people or tools within the user's mandate. The map organizes work; it does not grant authority. The names are optional.

Role Job What they check
L1 Firewall Contradiction isolation Does this claim contradict a settled [A]? Is the tone overconfident?
L2 Truth-Cut Evidence-tier discipline Is every claim tiered? Is any [C] presented as fact?
L3 Audit Route verification Do links point to active canon? Are archive files cited as live?
L4 Executor Build and deploy Does the builder run? Does the gate pass? Is the reported scope exact?
L5 Architect Schema and navigation Does the site structure match the canonical tree? Is the map honest?
L6 Compressor Archive and tombstone Are superseded claims preserved with traceable replacements? Is archive-first discipline followed?
L7 Witness Boundary observation Does the public face match the internal discipline? Is the packaging honest?

Naming footnote: in the source tradition's comparative table these seven roles carry Sanskrit ladder names — L1 Caṇḍāla, L2 Śūdra, L3 Vaiśya, L4 Kṣatriya, L5 Brāhmaṇa, L6 Sādhu, L7 Ṛṣi — used strictly as functional labels: function, never birth and never rank. The functional names above are the canonical public vocabulary.

Evidence tier [S]: This table is a structural scaffold — it describes a possible dispatch grammar, not a claim about how the work was actually done. The repository history and dated build receipts are the evidence for what was built.

Evidence tier [B] — command-line evidence

Fork and Verify

You do not need to trust this site. You need to trust your own terminal. Here is the exact sequence to clone, build, and verify.

1

Clone the repository

git clone https://github.com/circumvectio/emergentism.git
cd emergentism/12_PUBLIC_SITE
# Or fork first, then clone your fork
2

Check derived route files

python3 -B build_pwa.py --check
python3 -B build_atlas_index.py --check
# Both commands are read-only in --check mode.
3

Build and verify the candidate

python3 -B build_release.py
python3 -B predeploy_check.py --release .release
# Standard-library Python only; either command exits nonzero on failure.
4

Rebuild and compare the digest

first="$(cat .release/RELEASE_SHA256)"
python3 -B build_release.py >/dev/null
test "$first" = "$(cat .release/RELEASE_SHA256)"
# No output and exit 0 means the same checkout reproduced the same bytes.

[S] The build and verification scripts use only Python's standard library. If any command above fails, that is an audit finding rather than a footnote. The commands establish local reproducibility only; they do not prove a live domain or authorize publication.

[S] — generated integrity record

What the release records

build_release.py writes one generated record: .release/RELEASE_SHA256, a deterministic digest of every other released path and byte. The terminal reports the file count and digest. It deliberately embeds no timestamp, commit identity, signature, or tier distribution.

Source revision git rev-parse HEAD
Timestamp not embedded
Files copied reported by builder
Gate status reported by gate
Tree digest .release/RELEASE_SHA256
Release boundary release-manifest.json

Boundary: the digest proves byte identity only when independently recomputed over the same path ordering. Repository revision, actor, mandate, and live publication must be established separately.

Evidence tier [S]: A complete publication receipt would additionally name the principal, mandate, scope, actor, custodian, consequence bearers, reversibility, and contest path. This page does not claim that such a receipt exists.
